# AI 时代，前端的「失落十年」会重演吗？

2026 年 5 月，一篇题为「Is AI causing a repeat of Frontend's Lost Decade?」的文章在 Hacker News 上收获了 407 分和 334 条评论。作者 Mauro Bieg 提出了一个让前端开发者坐不住的核心问题：**AI 正在对编程整体做当年框架对前端做的事——去技能化（deskilling）**。门槛降低了，但专业技能也跟着贬值了。

这不是一个新故事。十年前，Alex Russell 站在 Google Chrome 团队内部喊出了「Frontend's Lost Decade」。那时他指控的是 React 等 SPA 框架让 Web 性能倒退到「可接受但糟糕」的水平。十年后的今天，AI 编码工具正在以十倍的速度重复这段历史。

这一次，会重演吗？还是会走向不同的结局？

## 回放：2010s，前端为什么「失落」了？

要理解今天 AI 带来的焦虑，得先回到当年的前端框架时代。

2008 年到 2010 年，前端还是需要一套完整技能的专门领域：你需要懂语义 HTML 的文档结构、CSS 的盒模型和层叠规则、跨浏览器的兼容性黑魔法、无障碍访问（a11y）的 ARIA 标注、渐进增强的策略思维，以及在 56Kbps 网络上做性能优化的手感。Chrome DevTools 的铁杆用户会逐帧分析渲染管线，Opera Mini 的适配细节能被讨论一个下午。

然后 React 来了。

React 的核心理念是一个激进的抽象：**把浏览器当成编译目标（compile target）**。你不需要理解 DOM 的生命周期，不需要关心 CSS 的级联规则，不需要思考事件冒泡和代理——框架把这些都「抽象掉了」。任何后端 Java 工程师经过两周培训就能转前端，而且产出足够「能用」。

代价被转嫁到了用户身上。Alex Russell 在「Performance Inequality」系列中反复展示的数据触目惊心：年收入 1000 美元的普通用户用着 150 美元的手机，却要加载 2MB+ 的 JavaScript bundle，在 3G 网络上等待 8 秒白屏。这个世界上的大多数用户，以他们的设备和网络条件，「现代 Web」实际上是「不可用的 Web」。

更深的代价在开发者这边。Chris Heilmann 所说的「front of the frontend」——那种与浏览器深度对话的手艺——在框架大潮中几乎被冲刷殆尽。老前端讲起「IE6 的 `hasLayout` bug 是如何锤炼出对渲染机制的深刻理解的」，新一代开发者只会耸耸肩：「让框架处理就好了。」而框架确实处理了——用 200KB 的运行时和一个 Virtual DOM 的代价。

## AI 时代：抽象膨胀 2.0

Mauro Bieg 在文章里给了一个犀利的类比：**AI 编码就是 Stack Overflow 复制粘贴的延伸，不过是把「搜索 + 复制 + 粘贴」压缩成了一次回车键**。

这个类比精准得让人后背发凉。2000 年代末，「Google-fu」是一门真功夫——知道用什么关键词、筛哪些站点、怎么看一个回答是否靠谱。Stack Overflow 的出现把这种技能部分地「诺曼化」（Normanization）了：你不用很懂，照着高票答案复制粘贴就行。今天的 LLM 把最后一步也消灭了：你甚至不需要会粘贴，AI 直接帮你写好整段代码。

但如果只是「自动补全变聪明了」，那还不构成「失落十年」的威胁。真正的问题在于：**AI 生成的代码天生带有安全冗余，而这种冗余正在让前端 bundle 重新膨胀**。

HN 用户 `acters` 发现了一个让人哭笑不得的例子：Claude 在前端代码中生成了「模糊背景动画」——关键帧指定了 `backdrop-filter: blur()`，并且针对 240Hz 显示器做了每秒 240 帧的重绘优化。任何一个人类前端看到这段代码的第一反应是：等等，这里真的需要 GPU 每秒钟重新绘制 240 次吗？答案是否定的。但 AI 不会问这个问题。它只是在训练数据里见过「动画要流畅」的模式，然后机械地应用了最高规格的参数。

另一个例子是 `paulmakeswebsites.com` 上对 Shadcn Radio Button 的解剖。一个原生 HTML 里只需要 `<input type="radio">` 加上一个 `<label>` 就能完成的事，在 Shadcn（一个流行的 React 组件库）里展开成了数百行代码。AI 在空白项目上初始化技术栈时，会不假思索地引入 TanStack、MUI、Tailwind、Shadcn——不是因为项目需要，而是因为「反正免费的 token 不用白不用」。

这跟 2015 年 Webpack 的「配置地狱」如出一辙，只是这次的驱动力从「社区 FOMO」变成了「AI 的机械记忆」。

## 开发者正在失去代码的「知情权」

HN 上有一条评论振聋发聩。用户 `classified` 说：**「每次你说『LLM 比我更懂 X』，你就等于承认了：你没有资质判断 LLM 的输出是否正确。」**

这是一个残酷的认知闭环。LLM 能写出看起来正确的 React 组件——有 `useState`、有 `useEffect`、有 `useCallback`、甚至有看似合理的测试文件。但如果追根究底地问：这个 `useEffect` 的依赖数组真的完整吗？这个 `useCallback` 真的有性能收益还是纯粹增加心理负担？AI 给出的答案可能看起来头头是道，更可能的是它自己也不确定，只是把见过的最常见模式拼了出来。

用户 `d0liver` 说得更直接：**「把代码拆开逐行研究、理解自己认知边界的过程才是真正有价值的——你跳过的正是这个环节。」**

这种「知情权丧失」的后果不止是个人技能的萎缩。用户 `customguy` 提出了一个更长远的忧思：如果所有人都用 LLM 写代码，而越来越少的人写教程、做开源、分享踩坑经验，那 LLM 训练数据的源头就断了。「LLM 从 LLM 学习的效果，我们已经从模型退化的文献里知道并不好。」

## 两条分岔路：2026 年的三种场景

回望 2026 年夏天，前端的未来可能走向三个方向。

**场景一：重演。「失落十年 2.0」如期而至。**

AI 生成的 React/Next.js 代码主导一切，bundle size 在 AI 的「安全冗余注入」下逼近 5MB 中位线。开发者从「写代码的人」变成「AI 输出的质检员」——不是把关质量，而是把关「能不能跑」。性能被放任不管，因为「AI 写了就好了，改不动」。Alex Russell 在 2036 年又开了一场演讲，标题换成了「Frontend's Second Lost Decade」。

这种场景的危险信号已经出现。`hombre_fatal` 在 HN 上为 AI 辩护说「AI 能写测试、能做 TDD」。但 `majormajor` 立刻反驳：「AI 写的测试只是视觉上令人印象深刻，里面全是无意义的 mock 和不重要的场景。」更可怕的是，开发者看了 AI 生成的一排绿色的 ✓，产生了一种「项目质量没问题」的幻觉。

**场景二：分化。好的人更好，差的人更差。**

`dershe` 在 HN 上提出了一个三层模型，值得一帧帧看：

1. **第一类开发者**：能在底层写得好，也能用库更快地写。AI 对他们来说是加速器。
2. **第二类开发者**：没有库做不了，但有库就能做出东西。AI 给了他们低保。
3. **第三类开发者（「乌合之众」）**：没有库不可能做，但有了 AI 现在能拼出半成品。

在 JS 生态里，第三类人远超前两类之和。AI 的出现让第三类的数量进一步膨胀——以前不会写代码的人，现在能靠 AI 快速拼出一个「看起来能跑」的应用。

分化意味着：顶层工匠的市场越来越小但价值越来越高，底层「AI 操作员」的议价权被无限压缩，中间层消失。这和过去十年「全栈开发者」消灭「纯前端」的过程一模一样，只是这次加速器从框架换成了 LLM。

**场景三：Bauhaus 时刻。行业学会与 AI 合作，而非被它取代。**

如果说前两种场景都是被动等待冲击的到来，那么第三种场景需要主动选择——这正是 Mauro Bieg 在文章结尾给出的富有希望的历史类比。1919 年，面对工业流水线对手工艺的碾压，德国 Bauhaus 学校选择了与机器合作，而不是对抗。他们深入理解材料——钢、玻璃、混凝土——然后用工业化的方式创造出比手工艺时期更伟大的作品。

前端的「材料」是什么？是 HTML、CSS、JavaScript（或者说 ECMAScript），是浏览器的渲染管线，是网络协议，是无障碍规范。一个真正理解这些材料的开发者，不会抗拒 AI。他会在 AGENTS.md 里写好性能预算、a11y 检查清单、CSS 书写规范，让 AI 在约束下高质量地生成，然后自己审阅关键的架构决策。

在这个场景里，前端工程师的职业生涯路径会从「写代码」进化到「制定规则 + 判断质量」。类似于建筑师的演化：从亲手砌砖，到画施工图，到审阅建筑信息模型（BIM）——工作内容变了，但专业性的本质没有丢。

## 结语：这次不同，但押韵

Mark Twain 说「历史不会重复，但会押韵。」

AI 对前端的「去技能化」和十年前框架的「去技能化」在结构上惊人地相似：一个抽象层降低了准入门槛，把专业技能的护城河填平了，代价是被「抽象掉」的那些细节变成了谁也不会再关心的盲区。框架时代丢掉的是语义 HTML 和无障碍访问的性能预算，AI 时代正在丢掉的是对代码逐行理解的能力和做减法（少写代码）的勇气。

但这一次有三个关键不同。

第一，AI 的去技能化速度是指数级的，不是线性的。React 花了五年让后端开发者能写前端；Cursor 花了两年让不会写代码的人能写代码。留给从业者调整职业路径的窗口期比上个十年短得多。

第二，AI 生成的代码有一种**隐藏的「非确定性冗余」**。人类开发者引入冗余通常是有意为之的决策（「这个库未来可能用到，先留着」）。AI 引入冗余是训练数据的统计偏好在无意识层面导致的——它不知道自己在制造浪费。这种冗余，目前没有工具链能自动识别和清理。

第三，也是最关键的一点：**这次没有「框架 vs 手写」的二元选择了**。2016 年你还可以选择用 Vue 而不用 Angular，或者用 Svelte 而不用 React——你仍然在「框架」和「手写」之间选边。但在 2026 年，AI 已经渗透到代码生成、代码审查、测试编写、文档生成等全链路。你不用 AI，你的对手在用。这场竞赛没有旁观席。

所以，对于我们这些 2026 年的前端开发者来说，问题不是「要不要用 AI」——那是伪问题。真正的问题是：**你正在用 AI 加速什么？是在加速产出「勉强能跑的代码」，还是在加速自己成为更好的「材料理解者」？**

十年前，那些只掌握了 Angular CLI 的「全栈开发者」在框架换代后发现自己一无所有。十年后，那些只会对 AI 说「帮我写个登录页面」的人可能会发现，AI 不仅把你的工作做了，也把你的议价权一起带走了。

而此刻在代码中多问一句「这段 AI 生成的 `useEffect` 到底在解决什么问题」的人，或许正在为自己买下一张通往 Bauhaus 时代的船票。
